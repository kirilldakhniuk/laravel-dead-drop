# Local MySQL benchmark — 2026-09-20

The current PHP dump pipeline exported 1.139 GB of synthetic column values in
48.4–51.9 seconds across two runs. Both completed artifacts passed verification
of every retained payload and all row counts. This is a measured local baseline,
not a forecast for a 50 GB production database.

## Environment and workload

- Apple M1 Max, 32 GiB RAM, macOS arm64.
- PHP 8.5.7, Laravel 13.32.0, MySQL 8.0.33 on localhost.
- Dedicated benchmark MySQL process with a 256 MiB InnoDB buffer pool.
- PHP memory limit 512 MiB; actual package defaults: 1,000-row chunks, gzip level 6.
- Local artifact disk, one PHP export process, read-only MySQL snapshot.
- Timed `DumpRunner::run()`: planning, counts, redaction, serialization,
  compression, staging, local upload, and manifest writes. No queue wait time.
- Separate PHP processes per run; operating-system caches were not cleared.
- No production code changes or performance tuning between runs.

| Table | Rows | Logical input bytes | Payload |
| --- | ---: | ---: | --- |
| Narrow rows | 200,000 | 50,177,790 | Email, password, random text |
| JSON rows | 131,072 | 551,873,021 | 4 KiB random token plus JSON metadata |
| Binary rows | 8,192 | 536,902,573 | Independent random 64 KiB blobs |
| Total | 339,264 | 1,138,953,384 | |

MySQL reported 1,450,295,296 bytes of table allocation. Seeding took 33.6 seconds,
outside the timed exports. Logical bytes sum the source column values, with
integer IDs represented as text; they are not the NDJSON size or MySQL page size.
The JSON and binary payloads were retained, emails hashed, and replacement
passwords processed through the cached bcrypt transformer.

MB uses decimal units; MiB uses binary units. PHP allocator, process RSS, and
macOS memory footprint measure different things. The allocator figure alone
must not be presented as the full process memory requirement. None of these
PHP-process figures includes the separate MySQL server. CPU and query timings
are included in wall time, not additional time to add to it.

Binary-table completion took 30.61 / 27.37 seconds, including initial planning.
The subsequent JSON table took 18.84 / 18.63 seconds; narrow rows took
2.49 / 2.44 seconds. The tiny artifact-size difference comes from newly salted
replacement password hashes in each PHP process.

## What this supports

The pipeline completes a dataset larger than its PHP memory limit. Memory is
bounded by batches, but 1,000 wide blob rows still produced a 158 MiB allocator
peak. Export uses `chunkById()` callbacks; the import/verification reader uses
`yield` and reads rows individually. Wrapping the existing export batches in a
generator would not eliminate the memory occupied by each fetched batch.

PHP CPU time was close to elapsed time, while database querying occupied only
about two seconds. That makes compression and per-row processing the next
profiling targets for this workload. These measurements do not isolate their
individual CPU costs. Exact pre-export counts were under 1% of elapsed time
here, so removing them would not address the main measured cost. Smaller or
byte-aware batches are worth testing for wide rows; compression levels should
be compared before choosing a faster default.

Random binary data is deliberately hard to compress; about half this dataset
consists of such blobs. Results will differ for predominantly relational rows,
compressible text, remote MySQL, S3 uploads, concurrent production writes, or a
different machine. Two runs establish a baseline, not statistical confidence.

Verification streamed all 339,264 rows for both artifacts, checked primary-key
order, all payload SHA-256 checksums and email redaction, and verified one
replacement password hash per artifact. The synthetic database and large dump
files were removed after validation; the harness and measurements are retained.
